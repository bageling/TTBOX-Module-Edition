# 架构总览

> 本文档用中文解释 TTBOX-模块版的整体架构：系统分层、模块边界、依赖规则、为什么这样设计。

## 一、TTBOX 是什么（30 秒版）

TTBOX 是一台基于 **RK3588 芯片**的 AI 视觉盒子：
通过 **HDMI 线"看"电脑屏幕**，用 **AI（NPU）识别画面中的目标**，
然后（可选）**通过 USB 控制鼠标**（本阶段保持关闭）。

## 二、系统分层（从上到下）

```
┌──────────────────────────────────────────┐
│  Web 控制层   浏览器页面 ↔ Web服务 ↔ IPC    │
├──────────────────────────────────────────┤
│  功能插件层   web/preview/model/fan/wifi...│
├──────────────────────────────────────────┤
│  控制输出链   TargetSelector → Coordinate │
│              → Controller → MouseCommand │
├──────────────────────────────────────────┤
│  AI 检测链    Capture → RGA → RKNN →      │
│              DecodeNMS → Detection        │
├──────────────────────────────────────────┤
│  硬件层       RK3588 + HDMI RX + NPU + USB│
└──────────────────────────────────────────┘
```

## 三、第13阶段模块边界（正式版）

```
                    ┌─────────────┐
                    │   Capture   │  采集：/dev/video0 抓帧
                    └──────┬──────┘
                           │ Frame
                           ▼
                    ┌─────────────┐
                    │  Detector   │  AI 推理 + 解码（RKNN 细节全在内部）
                    └──────┬──────┘
                           │ Detection[]
                           ▼
                 ┌───────────────────┐
                 │  TargetSelector   │  从多个目标选一个
                 └─────────┬─────────┘
                           │ Target
                           ▼
                 ┌───────────────────┐
                 │    Coordinate     │  目标框 → 瞄准点（原图坐标）
                 └─────────┬─────────┘
                           │ TargetPoint
                           ▼
                 ┌───────────────────┐
                 │    Controller     │  目标点 → 误差 → PID → 鼠标命令
                 │   PID / future    │
                 └─────────┬─────────┘
                           │ MouseCommand
                           ▼
                 ┌───────────────────┐
                 │       Mouse       │  【本阶段停止】未来：写 HID 设备
                 └───────────────────┘
```

**每个模块只负责自己的事情**：
- Capture 只抓帧，不推理、不选择
- Detector 只检测，不选择、不控制
- TargetSelector 只选目标，不碰 RKNN/V4L2/Mouse
- Coordinate 只算坐标，不控制
- Controller 只算命令，不写设备
- Mouse（未来）只写设备，不算命令

## 四、模块依赖规则（必须遵守）

```
Core（核心库）
  ↓
Module Interfaces（模块接口：IController / IDetector / IHidOutput）
  ↓
Concrete Implementations（具体实现：PidController / TargetSelector / ...）
```

**禁止反向依赖**：

| 禁止 | 原因 |
|---|---|
| TargetSelector 依赖 Web | 选择逻辑与界面无关 |
| Coordinate 依赖 Mouse | 坐标计算与输出设备无关 |
| Controller 依赖 HID | 控制算法不知道也不关心写什么设备 |
| Detector 依赖 Web | 推理与界面无关 |
| Web 直接改 Core 内部状态 | 只能通过 RuntimeConfig（内存快照）热更新 |
| Plugin 直接改 Core 内部状态 | 插件只能调用公开服务接口 |

## 五、为什么这样设计（小白必读）

### 为什么 Detector 和 TargetSelector 分开？
- **Detector（检测器）**回答"画面里有什么"（输出 Detection[]）
- **TargetSelector（目标选择器）**回答"打哪个"（输出 Target）
- 分开后：换模型（yolo261n → 其他）只动 Detector，选择逻辑不用改

### 为什么 Coordinate 单独存在？
- 坐标系换算（模型坐标 → 原图坐标 → 瞄准点）是**最容易出错**的部分
- 集中在一处管理：比例、偏移、裁剪信息只有一个正式来源
- 禁止"AimThread 算一遍、Web 算一遍、测试再算一遍"

### 为什么 Controller 和 Mouse 分开？
- **Controller（控制器）**只计算 MouseCommand（纯数学，可测试）
- **Mouse（鼠标输出）**才负责写设备（未来）
- 分开后：可以换控制算法（PID/比例/滤波/预测），输出层不用改

### 为什么 MouseCommand 和 HID 分开？
- MouseCommand 只是一个数据结构（dx/dy/valid）
- 不知道也不关心如何写入 /dev/hidg*
- 好处：本阶段可以安全地"只算不写"，测试时打印/存 JSON 即可

### 为什么本阶段不打开鼠标注入？
- 真实鼠标注入是**不可逆的外部副作用**，必须等控制链逻辑全部验证无误
- 安全红线：`output_enabled=false`、`injection_allowed=false` 全程保持

### 为什么换模型不需要重写整个系统？
- 模型细节（RKNN/tensor/NPU core）全部封装在 Detector / ModelAdapter 内部
- 上层只看到 `Detection[]`（类别/置信度/坐标），与具体模型无关
- 换模型 = 换配置（model_path），上层代码零改动

## 六、统一数据结构（层间传递）

| 结构 | 定义位置 | 含义 |
|---|---|---|
| Frame | common/Types.hpp | 一帧图像（像素 + 元信息） |
| Detection | common/CoreContracts.hpp | 一个检测结果（类别/置信度/坐标） |
| Target | pipeline/Target.hpp | TargetSelector 选中的目标 |
| TargetPoint | pipeline/Target.hpp | Coordinate 算出的控制目标点 |
| MouseCommand | common/CoreContracts.hpp | Controller 输出的鼠标命令（dx/dy） |

> MouseCommand 与 HID 完全解耦：本阶段产生命令后直接停止（打印/JSON），不写设备。
